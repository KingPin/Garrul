# Languages and localization

What language your readers see, how it's chosen, and what is deliberately
never translated.

## Language is a property of the site, not the reader

A German visitor to an English blog gets an **English** comment box. This
is a decision, not a gap: a German composer sitting under English prose
reads as broken, and the comments below it will be in English anyway.

So `Accept-Language` and `navigator.language` are never consulted. Neither
is the reader's OS or browser setting. The only inputs are yours.

## Resolution order

The first of these that yields a supported locale wins:

1. `data-lang` on the mount element (or `?lang=` on the iframe URL)
2. The operator's `default_locale` setting, in *Settings*
3. Your host page's `<html lang>` — **reviewed locales only** (see below)
4. `en`

An unrecognized or unsupported tag falls back to English rather than
erroring, so a typo in `data-lang` degrades quietly.

```html
<!-- script tag -->
<div id="garrul" data-slug="my-post" data-lang="de"></div>
```

```html
<!-- iframe variant -->
<iframe src="https://comments.example.com/embed/my-post?lang=de"></iframe>
```

## Shipped locales

| Locale | | Status | Auto-selectable from `<html lang>` |
| --- | --- | --- | --- |
| `en` | English | Source | yes |
| `de` | Deutsch | Machine-seeded — not reviewed | no |
| `es` | Español | Machine-seeded — not reviewed | no |
| `fr` | Français | Machine-seeded — not reviewed | no |

**"Machine-seeded" means exactly that:** LLM output that no native speaker
has checked. What that tends to get wrong is register and consistency —
"Post" as a noun where it should be an imperative, formal address in a file
that is otherwise informal.

They ship anyway, because holding translations until a volunteer appears is
how a project ends up with none. But an unreviewed locale is reachable
**only** through an explicit `data-lang` and is never picked up from your
`<html lang>`. So the only person who ever sees unreviewed German is an
operator who typed `de` and therefore reads German.

Correcting one is the easiest useful PR in the repo, and it promotes the
locale to reviewed and auto-selectable —
[CONTRIBUTING.md](../CONTRIBUTING.md#translations-wanted).

## What it costs on the wire

English is compiled into the widget bundle as the per-key fallback, so an
English mount downloads no string table at all. Only a non-English mount
fetches one. Adding locales does not grow the bundle for readers who don't
use them.

## What is and isn't translated

**Translated:** the widget UI, API error messages, notification emails, and
feed templates.

**Never translated:**

- **Comment bodies.** They are what your readers wrote.
- **Numbers.** Deliberately not localized.
- **The admin UI**, and the Telegram operator bot. English-only by design —
  they are seen only by you.

## Timestamps

Timestamps stay **ISO everywhere they are data**: API responses, feeds,
email, and the `datetime` attribute.

The one exception is the reader-facing comment timestamp in the widget,
which renders a **relative label** — "2 hours ago" — via
`Intl.RelativeTimeFormat` in the site's resolved locale. The exact ISO value
is preserved in `datetime`, and the reader's own local wall-clock time is in
the `title` attribute on hover.

That surface is the one place where the ISO rule produced a wrong answer
rather than a neutral one: it previously showed `2026-08-12 14:33` in UTC to
every reader on earth with no timezone label, so a reader in Berlin saw a
comment posted a minute ago stamped two hours in their past.

Note the split: the *language* of the label is the site's, because that is a
property of your site. The *timezone* is the reader's, because that one
isn't — it's where they are standing.

## Plurals

Plural forms use `Intl.PluralRules` with a `{ one, other, … }` value shape,
so languages with more than two categories are expressible. The fallback
chain is: selected category → `other` → `one` → English.

## Adding a locale

See [CONTRIBUTING.md](../CONTRIBUTING.md#translations-wanted). In short:
copy `src/i18n/en.ts`, translate the values, and add the tag to the
supported list. The widget's own strings live separately in
`src/widget/strings.ts` — the widget cannot import from `src/i18n/`, so the
server imports the widget's table and serializes the merged result into
`/api/v1/config`.
